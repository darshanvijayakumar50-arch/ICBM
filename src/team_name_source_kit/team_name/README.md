# Track 03 – Sensor Jamming & Progressive Degradation

Pure-Python (standard library only) streaming IMU trajectory estimator. One pass over the CSV, one pose per input row.

## Run

```
python src/main.py <input> -o estimated_trajectory.txt --meta metadata.json
```
`<input>` = CSV file, a folder containing `imu0/data.csv`, or a `.zip` containing it.
No `pip install` needed (Python 3.8+). Column order (accel-first as in the organizer degrade script, or EuRoC gyro-first),
header (optional), timestamp unit and accel unit (m/s² or g) are auto-detected; override with `--order accel|gyro`, `--gyro-deg`.

Check + package:
```
python tools/validate_submission.py <input.csv> estimated_trajectory.txt
python tools/package.py team_name --run <input.csv>      # runs, validates, builds team_name.zip
```
Optional local scoring (needs numpy): `python tools/evaluate.py groundtruth.txt estimated_trajectory.txt`.
Rename the folder `team_name` to your real team name before packaging.

## Algorithm (how raw IMU becomes a trajectory)
1. **Init** (first 200 rows, the organizer protects the first 2 s): gravity direction -> initial roll/pitch, gravity magnitude, gyro bias. Yaw starts at 0, position at 0 (poses are in a gravity-aligned local world frame).
2. **Per sample**: spike gating (isolated jumps rejected), stuck-sample detection (identical rows), duplicate timestamps (dt = 0 -> pose repeated), timestamp-gap detection.
3. **Attitude**: quaternion gyro integration + Mahony gravity correction (roll/pitch) + gyro-bias integrator. Yaw is unobservable from an IMU and will drift.
4. **Position**: rotate specific force to world, subtract gravity, integrate. Because pure double integration diverges quadratically, the code uses: *leaky velocity*, *zero-velocity updates* (stationary detector on EWMA statistics) with accel-bias learning, a *position pull toward the start point*, and a velocity clamp. Leak strengths grow automatically as measured noise grows.
5. **Blind mode**: first row where all six values are exactly 0.0 latches failure.

## Tier mapping (what in the code satisfies what)
- **T1** (`run()` measurement path): attitude + leaky strapdown above; every row gets a pose with exact timestamps.
- **T2** (`if failed:` block in `run()`): after the all-zero latch, no measurement is used. Orientation continues at the last smoothed angular rate decaying with tau 2 s; velocity decays with tau 1.5 s and is integrated. Assumption: motion keeps its last trend and fades. Limitation: any change in the real motion is unknowable; error grows with time and the last velocity estimate is itself drift-limited. The latch is not tied to the "last 5 s" rule, so it works for whatever length the failure has.
- **T3** (`gap` handling + spike/stuck/bad-row logic): dropped rows show up as timestamp gaps; the filter integrates the true elapsed time using the mean of the samples on both sides of the gap and skips gravity correction across it. Rows are never removed from the output.

## Honest status
- **Tested only on SYNTHETIC data** generated by `tools/make_synthetic.py`, degraded with the organizer's `degrade_imu.py`. **Not tested on real EuRoC/TUM-VI** (not available in our build environment) and **not scored with the real `evo`** or hidden ground truth. Parameters in `P` at the top of `main.py` were tuned only on that synthetic data; retune with real data if you can.
- On synthetic data (90 s, 200 Hz, 17,500 degraded rows): output validated (row count, 8 columns, timestamps equal input x1e-9, |q| = 1 within 1e-9). Position ATE (own SE(3)-aligned scorer) is about 1.3 m, which is essentially **the same as a trajectory that never moves (1.3 m)**: severe degradation makes IMU-only position nearly unrecoverable, so the leak/ZUPT design mainly bounds the error rather than recovering the path. Orientation error was ~2.6 deg mean before failure and ~10 deg during the 5 s blind window.
- If the real evaluator does not align trajectories to ground truth (evo `-a`), absolute pose will not match, since we start at the origin with yaw 0.
- Duplicate input timestamps produce duplicate output timestamps (one pose per IMU frame, as the spec says). If evo complains about repeated timestamps, tell the organizers/ask whether to keep them.
- **Runtime**: ~1.3 ms per second of data measured on this build machine (budget 20 ms/s). Your machine will differ.
- **Memory**: Python heap peak is ~0.75 MB (tracemalloc), but process RSS is ~14 MB here, of which ~10-11 MB is the bare Python interpreter. **An 8 MB peak cannot be met by any CPython process on our measurement**; whether this costs points depends on how the judges measure memory. Running with `python -I -S` trims about 1 MB. A C/C++ port would be needed to be strictly under 8 MB, but you said Python only.
- The Windows memory-measurement path in `main.py` is untested.
